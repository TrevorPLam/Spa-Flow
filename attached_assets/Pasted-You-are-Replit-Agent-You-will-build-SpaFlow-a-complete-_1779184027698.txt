### 2. WHAT IT DOES (CORE FUNCTIONALITY)
Build all of the following features into a single Next.js application with a PostgreSQL database.

#### a. Client Profile Management
- Create and manage profiles for **members** and **non-members**.
- Profile fields: name, DOB, address, government document number, membership status (none, one-time, six-month), notes (long text or JSON field).
- All sensitive PII (DOB, address, document number) must be encrypted at the application level before writing to the database. Use the envelope encryption pattern with a Data Encryption Key (DEK) generated per record, encrypted by a Key Encryption Key (KEK) stored in an environment variable (`ENCRYPTION_KEY`). The KEK is a 256-bit key, base64-encoded, stored in Replit Secrets.
- The system must use JWT authentication stored in `HttpOnly`, `Secure`, `SameSite=Strict` cookies. No PII in localStorage.

#### b. Membership Management
- One-time membership: $13 (valid for a single visit).
- Six-month membership: $42 (auto-calculated expiration date from purchase date).
- Memberships must be linked to the client profile. On check-in, if a non-member purchases a membership, the system assigns it and updates their status.

#### c. Locker & Room Management
- There are exactly **167 lockers** and **38 private dressing rooms**.
- Both lockers and rooms have a **6-hour rental time limit**, which can be **renewed for another 6 hours** or **surcharged for a 2-hour extension**.
- Track real-time occupancy status for every individual locker and room (Available, Occupied, Reserved).
- When a locker or room is assigned, the system records the start time. The front-desk UI must visually indicate occupancy and remaining time.

#### d. Dynamic Pricing Engine
Implement a pricing service as a pure function (no side effects) that takes the following inputs and returns the price before tax:
- `customerType`: MEMBER or NON_MEMBER
- `productType`: LOCKER or ROOM
- `startTime`: JavaScript Date
- `clientAge`: number (derived from DOB)
- `hasBirthdayToday`: boolean (derived from DOB and current date)

**Pricing Rules:**
- **Weekday** (Monday 8:00 AM to Friday 4:00 PM, excluding holidays/special events – for v1, ignore holiday list).
- **Weekend** (Friday 4:00 PM to Monday 8:00 AM).
- **Locker:**
  - $15 on weekdays between 8 AM and 4 PM (Mon-Fri).
  - $20 on weekdays outside that time window.
  - $24 on weekends.
- **Room:**
  - $25–$34 on weekdays. (Use the midpoint $30 for simplicity, or allow a configurable range; at minimum, default to $30.)
  - $28–$37 on weekends. (Default to $32.)
- **Specials (server-side validated only):**
  - **18–24 Special:** Valid for clients aged 18-24 (inclusive). On weekdays, locker is free ($0). On weekends, locker costs $7. (Only applies if they purchase a one-time membership; if they don't have one, prompt to buy it first, but calculate the price accordingly.)
  - **Birthday Special:** If the client's birthday is today (DOB month and day match current server date), the locker fee is $0, regardless of other rates. Valid ID required – the document number in the profile acts as verification.
- **Membership Discount:** One-time membership holders pay member pricing for that day. Six-month members always pay member pricing.
- **Tax:** Not included in these prices. Tax must be calculated and displayed separately at checkout. For v1, use a flat 8.875% (NYC rate) or a configurable environment variable `TAX_RATE`. Do not forget to add tax to the total amount sent to Square.

#### e. Check-In & Check-Out Workflow
- A staff member looks up a client by name, phone, or member ID.
- If the client has no membership, staff can sell a one-time membership ($13) as part of the check-in process.
- The system shows available lockers and rooms. Staff selects the desired type and specific number (if available).
- Before assignment, the pricing engine calculates the amount due based on the client's profile and current time.
- **Square Payment:** The frontend uses the Square Web Payments SDK to tokenize the card. The token is sent to the backend, which calls Square's Payments API with an idempotency key. The transaction is stored locally linked to the client and the rental.
- Upon successful payment, the locker/room is marked Occupied, a session record is created with start time, and the rental begins.
- **Check-Out:** Manually done by staff (or automatically after time expires – implement a background job using `node-cron` or similar to check every minute for expired sessions and mark them as Available). On check-out, record end time and free the resource.

#### f. Waitlist Management
- When all 38 rooms are occupied, a client can be placed on a **FIFO waitlist** for a room.
- A client on the waitlist can simultaneously have a locker (they are waiting for a room upgrade).
- When a room becomes available (check-out or expiration), the system must **atomically** assign it to the next person on the waitlist.
- Use a PostgreSQL function with `SELECT ... FOR UPDATE` to prevent double booking.
- Once assigned, the system must send an SMS notification to the client (use Twilio or Plivo — see environment variables). The message: "SpaFlow: A private dressing room is now available for you. Please proceed to the front desk within 15 minutes."
- If the client does not respond within 15 minutes, the room is released back to Available and the next person on the waitlist is notified. Implement this with a scheduled job that checks for unconfirmed assignments.

#### g. Additional Purchases (POS)
- Sell individual products: snacks, toiletries, novelty items. Maintain a simple product inventory (name, price, stock count).
- At checkout, staff can add products to a client's bill. The same Square tokenization flow handles the total payment.
- All purchases (rentals and products) are stored in a unified transactions table and linked to the client profile.

#### h. Role-Based Access Control (RBAC)
Two roles: `STAFF` and `MANAGER`.
- **STAFF**: Can create clients, check in/out, process payments, view basic profile info (masked PII except name), access waitlist, sell products. Cannot edit pricing rules or view full PII fields.
- **MANAGER**: Full access to everything, including encrypted PII viewing (decrypted in the app), pricing configuration, and audit logs.

#### i. Audit Logging
- Log every critical action: profile creation, PII access, check-in, check-out, payment, waitlist addition/assignment, role changes.
- Include timestamp, user ID (staff), action, resource ID, and a brief description.
- Store in an `audit_logs` table. This is essential for compliance.
